## 1. 行业权威分类：不同目的，联合使用

**不存在单一被所有汽修机构认可、覆盖电子故障码、机械症状、真实根因、维修价值的统一分类树**。建议采用不同权威工具的互补作用，而不是套用 DTC 分类当作全部故障：

1. **SAE J2012 / ISO 15031-6**：DTC 标准化命名和电子故障索引。P（动力总成）、B（车身）、C（底盘）、U（网络）等编码族适用于其规定范围；制造商专属信息需标识适用的品牌/车型/年款/控制模块/版本。DTC 表明监测异常，**不是根因的充分证明**。
   - SAE J2012（2025-09）：https://saemobilus.sae.org/standards/j2012_202509-diagnostic-trouble-code-definitions
   - ISO 15031-6:2015：https://www.iso.org/standard/66369.html
2. **ISO 14229-1:2026（UDS）**：车载诊断服务与 DTC 相关状态/记录的读取框架，用于解释何种电子证据存在；**不是整车故障症状分类树**。
   - https://www.iso.org/standard/87962.html
3. **ASE A1–A9 维修技师任务体系**：以实际修车能力及工作任务为导向，适合发现用户问题、覆盖遗漏和可解释的维修价值；其分类也不是全部原因分类。
   - https://ase.com/tests/a1-a9/
   - https://www.ase.com/press-releases/ase-a-series-task-list-surveys-help-drive-changes-to-future （36,000+ 专业人士参与的维修任务执行频率调研；不能把调研结果伪造成具体故障发生率）
4. **OEM 症状/故障码/故障现象诊断**：具体车型的“客户主诉 → 工况 → 是否有 DTC → 诊断流程与适用条件”，适合定义维修场景；引用时标明车型/年款/修订版本。
   - GM 策略诊断公开案例：https://estimate.mymitchell.com/GMC/document/1/9/5/7/6/100314543_1957622_14831429.html
5. **AIAG/VDA FMEA 与 SAE J1739**：功能、失效模式、影响、原因的因果分解；Severity/Occurrence/Detection 与 Action Priority 供风险分析参考，不能照搬为维修知识写作价值分数。
   - https://www.aiag.org/training-and-resources/manuals/details/FMEAAV-1
   - https://saemobilus.sae.org/standards/j1739_202605-potential-failure-mode-effects-analysis-fmea-including-design-fmea-supplemental-fmea-msr-process-fmea

## 2. 故障是知识生成入口，非唯一分类层级

**四种不同的“是什么”必须区别**：
- **Symptom / Complaint**：车主/技师观察到的异常（如冷车启动困难、换挡冲击、制动距离异常）。
- **Detection / DTC**：控制器检测/记录到的异常及其状态；有些故障没有 DTC。
- **Failure mode / Mechanism**：功能怎样失效及物理/控制机理（如压力建立不足、点火失火、执行器迟滞）。
- **Cause / Context / Effect**：具体原因、车辆适用范围、环境工况、影响与风险；不同原因可能共享症状，一个原因可引发多个症状。

不要将“某症状=某 DTC=必须更换某部件”当作一对一规则。不同类别之间用多对多引用和生成任务依赖表达，**不设置领域×故障类型的固定组合配额**。

故障候选名称应尽量采用实际维修语言；允许一个任务同时涉及机械、电子与液压。ASE 子系统仅用于定位和查漏，不作为强制每类多少条的生成指标。

## 3. 两种 DAG：知识依赖与调度依赖分开

**知识 DAG（理解所需的真正前置关系）**：基础机理 → 故障机理 → 症状竞争解释 → 证据鉴别/维修决策边界。按可读 Markdown 文件生成，相关知识多对多交叉链接。

**执行 DAG（工作顺序）**：实际故障候选收集 → 任务价值判定 → 按价值与依赖选择任务 → Markdown 生成 → 发现重要知识缺口后增量再规划。优先级决定“先做什么、写多深、复核多少轮”，**不应该虚构领域知识的因果依赖**。

一个真实故障可能生成多个专题任务，多个故障共用的前置知识只生成一次；遇到循环依赖时提炼共享基础任务或拆成递进版本。

## 4. 价值调度：不能把“常见”与“重要”混为一谈

### 4.1 评价因素（规划内部启发式，非行业标准评分）

| 因素 | 含义 | 如何得知 | 缺失时 |
|---|---|---|---|
| `F_frequency` | 目标车型/车龄/地区/里程背景下维修故障发生或维修请求频率 | 优先真实工单、保修索赔或有分母的车队数据；ASE 的任务频率仅间接提示维修活动量 | `UNKNOWN`，不可凭印象写“高频” |
| `V_repair_value` | 诊断/维修可避免的损失、人工与零件成本、误修/重复返工成本、停驶损失 | 实际工单费用/工时、OEM维修案例、明确的需求场景 | `ESTIMATED` 并说明假设 |
| `S_safety` | 人身、行驶、环境及法规风险 | 召回、官方安全公告、OEM 风险及明确的功能后果 | 单列风险；可信高风险可直接提高优先级 |
| `D_diagnostic_difficulty` | 原因多、误诊代价大、跨系统、证据获得困难 | 真实诊断流程、TSB 误诊线索、服务案例 | 低置信度 |
| `B_applicability` | 对目标车群有多大适用性 | 车型/年款/动力类型/地域/保有量或市场构成 | `UNKNOWN` |
| `G_knowledge_gap` | 已有知识能否解释该故障、任务带来多少非重复增量 | GitHub 当前 Markdown/历史候选差量及具体未解问题 | 先做有限探索 |
| `C_confidence` | 频率、价值、适用性和资料是否真的有证据 | 原始数据、证据范围/日期、样本覆盖 | 保持低置信度，不伪造数值 |

**推荐策略（先安全与真实价值，后加权排序）**：
1. `SAFETY_CRITICAL`：若有可信安全后果且汽修服务有实际知识需求，优先建立非执行的风险识别/适用条件/证据辨识任务；但 OEM 高压、制动、气囊等不可在没有车型/资质依据时生成具体危险操作步骤。
2. `HIGH_VALUE`：高可信的高频且高维修收益；**或**频率不高但误修损失大、跨系统诊断难、停驶代价大。进入深度生成和跨机理分支。
3. `STANDARD`：普通故障，生成足够解释问题的基础知识与边界；深度由后续证据和问题缺口调整。
4. `EXPLORE_UNKNOWN`：数据不足或新技术故障，先生成“如何认识/区分此问题”的有限研究内容，再搜寻可用依据；不能因为低观测频率永久不做。
5. `DEFER`：明显重复、目标汽修场景缺少实际关系或尚无足够信息可写有意义内容；记录原因，不假称已完成知识。

若希望做可计算内部排序，可在**非安全类**使用 0–5 的启发式粗评分（F、V、D、B、G）并为每个值注明证据级别，推荐 `P=0.25F+0.25V+0.20D+0.15B+0.15G`，**这不是 SAE/AIAG 官方公式**。缺少可信证据时不应精确计算；应使用“待证/先采样/无法排序”的状态。安全风险先独立分流，绝不能让低 F 抵消高 S；数据置信度用于决定是否可据此排序，不是单纯惩罚缺少数据的新问题。

**生成预算是结果而非预先条目配额**：高价值任务可以延伸子问题、生成更多因果反例、采用多轮独立提示词提炼、加深维修误判案例；普通任务充分回答即可；未知任务先作小范围探索。固定字数、条数、每类配额都不可作为完成标准。

### 4.2 实际频率证据的正确来源与偏差

- **首选**：真实维修工单与车辆暴露分母（具体车型、年款、里程、地区、统计时间窗，重复进厂去重）；可计算服务请求率，不能自动等同零部件失效率。
- **补充**：OEM 保修统计、服务公告/TSB、适用的车型召回、专业技师任务调查。TSB 代表发布过的已知问题与服务信息，**不能用 TSB 数量直接当发生率**。
- **公开线索**：NHTSA 投诉、调查、召回、Manufacturer Communications；投诉有自选择和报告偏差，车辆群体规模/使用强度若未知，不可直接给“故障概率”。US-specific 数据不可无证明外推到 Myanmar 或其它目标市场。
  - NHTSA 数据/API：https://www.nhtsa.gov/nhtsa-datasets-and-apis
  - Manufacturer communications：https://www.nhtsa.gov/vehicle-manufacturers/manufacturer-communications
  - Recalls：https://www.nhtsa.gov/recalls
- **防止错位**：维修“常见”可能指工单量、车辆发生概率、技师处理频次、用户抱怨率或配件销量，至少在任务评价前明确统计口径。

## 6. 单个节点的最小 Markdown 交付

只要求 `.md`，不要求其它文件格式。每个节点的内容围绕**本次专业问题**自然组织，解释有效工作机理、故障机理、条件差异、多个可能原因、证据与误区、维修收益的具体来源以及可继续的未知问题。正文不强制知识类型标签。

任务元信息只需在本项目的 Markdown 计划中记录：唯一任务 ID、问题、前置、故障/症状别名、相关 DTC（可无）、适用车辆范围（可 UNKNOWN）、证据级别、优先级理由、可交付文件路径、当前 Claim、完成条件、后续问题。

生成后由程序检查实际文件可读、引用路径及任务依赖，不将这一轻量交付检查冒充第二阶段的专业事实认证。
